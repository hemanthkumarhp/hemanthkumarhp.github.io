Case study — Automation

ReportSense v4.1 — deterministic first, AI only when needed.

An n8n workflow that reads the partner-reports inbox, figures out which scheduled report each email is, and stamps the delivery into PulseOps — so the on-time-delivery numbers on the dashboard update themselves.

My role
Problem definition, matching strategy, accept-rule thresholds, failure-mode handling, iteration from v1 to v4.1
Status
In production, feeding PulseOps daily
Stack
n8n · JavaScript code nodes · PulseOps webhook API · OpenRouter LLM (built, currently switched off)
Design rule
Refuse to guess. An ambiguous match becomes visible work, never a silent verdict
Scale
5,982 emails over 125 active days · 90.2% handled with no human touch

§01The problem

Every day, 50–80 partner reports arrive by email against a delivery schedule. Tracking them used to mean a person reading subjects and updating a tracker — error-prone, late, and unverifiable. Worse, subject lines are messy: abbreviations, aliases, forwarded threads, recalled messages, and "report will be delayed" emails that must not count as deliveries.

This was my own daily task. I read that mailbox every morning, recorded the actual delivery time of 60–100 scheduled reports into an Excel tracker by hand, and presented the compliance position in the next day's meeting. It took about 45 minutes a day. It now takes about five — reviewing the handful of emails the matcher declines to decide.

§02How it works

  1. Ingest & deduplicate IMAP inbox trigger; duplicate messages dropped before any processing.
  2. Fetch the day's catalog once The report catalog and matching profiles are pulled from the PulseOps API and cached per IST day — one fetch, not one per email.
  3. Classify the email Regex patterns split report deliveries from recalls ("please ignore") and delay notices ("will share shortly"). The delivery timestamp uses the IMAP arrival time — not the sender's claimed time — so stamps can't be gamed.
  4. Match deterministically TF-IDF cosine similarity between the subject and per-report profiles. Accept only if the top score clears a floor and beats the runner-up by a margin — a high score that's barely ahead of second place is not a confident match.
  5. Route the unsure ones to a human Anything that fails the accept rule goes to a review queue in PulseOps, where a person resolves it — and that correction feeds the next profile rebuild. An LLM fallback exists for this branch but is currently switched off; see below.
  6. Post to PulseOps Matched deliveries are formatted and POSTed to the PulseOps webhook API, updating the report tracker in near-real-time.

§03Decisions worth explaining

Score and margin, not just score
Early versions matched on keywords and accepted the best hit. The failure mode was two similar report names ("Order Load — North" vs "Order Load — South") both scoring high. Requiring a gap between first and second place is what actually prevents wrong stamps.
IMAP INTERNALDATE for the delivery stamp
The email's Date header says when the sender claims to have sent it. The mailbox arrival time says when the report actually arrived. For an SLA metric, only the second is honest.
The LLM fallback is built, and currently switched off
Deterministic code is testable and free; LLM calls are neither. I built the fallback, ran it, and then disabled all four nodes — at roughly three unmatched emails a day, resolving them by hand costs less than an API call on every low-confidence mail. It is a cost decision, not dead code, and re-enabling is a toggle rather than a build. The honest counter-argument is below: switching it off also removed the buffer that would have absorbed the drift.
From LLM-first to deterministic, over four generations
v1 matched entirely with an LLM because it worked immediately and I did not yet understand the report vocabulary. v2 and v3 moved to fuzzy matching with the model as backup. v4 replaced it with TF-IDF profiles built from the catalog itself. The direction of travel is the point — every generation moved work from the model to inspectable code as the domain became better understood, which made it cheaper, testable, and explainable.
Four versions to get here
v1–v2 used hand-maintained keyword lists in Google Sheets; every new report meant editing keywords. v4.1 builds TF-IDF profiles from the PulseOps catalog itself, so adding a report in PulseOps is all it takes.

§04Outcome

  • Report deliveries stamp themselves into PulseOps; the tracker no longer depends on a person reading an inbox.
  • Recalls and delay notices are classified instead of miscounted as deliveries.
  • No AI call is made in normal operation — the matching that runs in production today is entirely deterministic and inspectable.

§05When it drifted, and what I did

This is the part I'd most want to be asked about. The matcher degraded silently over roughly three months, and catching it was not automatic.

  • Detected. The share of emails falling through to manual review climbed from 2.0% in April to 15.0% in the week of 20 July, and a backlog of 218 unmatched mails accumulated between 26 June and 25 July. Nothing alerted — the number was there to be read, and reading it was the job.
  • Diagnosed. I classified all 218 failures into a taxonomy with counts: exact-score ties from duplicate profiles (74), reports missing from a stale snapshot (54), margin collapse between parent and sibling reports (60), vocabulary gap (27), no tokens matched (3). The root cause was not the matcher. The profile snapshot it read was written only by a manual admin button; the nightly job rebuilt the delivery schedule but never rebuilt the profiles. The matcher was scoring correctly against stale data.
  • Quantified before building. I replayed the matcher offline against a current, de-duplicated profile set: 181 of 218 resolved (83%) — with no change to the score or margin thresholds.
  • Rejected the obvious fix. Lowering the accept thresholds would have cleared the backlog and looked like a fix. It converts correct rejections into silent wrong stamps — trading a visible review queue for invisible bad data in an SLA metric. Worse failure, quieter.
  • Verified on the same metric. Review rate fell from 15.0% to 6.3% the following week and has held between 5% and 8% since.

Honest status: this was diagnosed and mitigated, not permanently closed. The recovery came from repointing the workflow and rebuilding profiles by hand. Automating that rebuild is the next change — until it ships, the drift can recur.

§06What I'd change

  • Automate the profile rebuild. This is the real fix for the drift above and it hasn't shipped. The rebuild still depends on someone pressing a button; until it runs on a schedule, the same failure can recur.
  • Test the accept rule. Coverage on the matcher is one parameterised test over the tokenizer. The scoring and the two-condition accept rule — the logic that actually decides things — are untested. The review queue catches the consequences, which is why this survived, not a reason it should.
  • Re-examine switching off the LLM. The decision was right at two or three misses a day and expensive when the miss rate hit 15%, because it removed the buffer that would have absorbed the drift. The better design is probably to re-enable it with a spend cap rather than leave it off.
