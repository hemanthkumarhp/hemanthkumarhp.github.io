Case study — Data validation

T1 Commercial DSR Validator — zero errors since adoption.

A daily sales report goes to the client every day. It used to ship on trust and spot-checks. Now it ships after a validator recomputes all 18 derived fields from reference data and confirms they match.

My role
Defined the validation rules and reference logic, specified the outputs, tested against months of real reports
Status
Run daily before the report is delivered
Stack

Tests

§01How I got this work

A developer had been assigned the automation for this report and left the company; the script he left behind was never usable in production. My manager gave the work to me rather than rehiring for the role, and handed over the departed developer's code — on the strength of the two systems above.

I was asked for a validator, not a rewrite. So I spent two working sessions with the analyst who owns the report deriving what “correct” actually means, field by field, and built against that. Two of the eighteen field mappings had competing candidate columns in the source workbooks; we resolved them by testing both against live data, and the verdicts are annotated in the code.

§02The problem

The Daily Sales Report is client-facing: 18 of its columns are derived from a quarterly template and a master mapping workbook. A wrong lookup or stale mapping meant a wrong number in front of the client — found, if at all, after delivery. Manual spot-checks caught some errors and missed others, and every check cost analyst time the team didn't have.

The check before this existed was the analyst doing the same comparisons by hand in Excel — about 30 minutes a day, sampled rather than exhaustive, and error-prone in exactly the way that matters: it found the mistakes you thought to look for. In the fortnight before the build, the team took two or three escalations from the client over inaccurate data in this report.

§03How it works

  • Reads exactly three Excel inputs — the template, the MTM master, and the day's DSR — identifying each by filename pattern, and refuses to run on ambiguous input.
  • Recomputes all 18 derived columns independently from the reference workbooks and compares them cell-by-cell to what the DSR actually says.
  • Writes one output workbook with a summary sheet, a data sheet listing every failing row with expected vs. actual values, and a warnings sheet for rows it can't verify (e.g. a model missing from the master).
  • Logs every run to a timestamped file, so "was it validated?" is always answerable.
  • Ships with a README written for non-technical colleagues — the tool is only useful if the team can run it without me.

§04Decisions worth explaining

Recompute, don't sample
Spot-checking finds the errors you guessed might exist. Recomputing every derived cell finds the ones you didn't — which is the category that reaches clients.
Warnings are separate from failures
A row the validator can't verify is not the same as a row that's wrong. Mixing them teaches people to ignore the report; separating them keeps failures loud.
Unit tests on the validator itself
A validator with a bug is worse than no validator — it manufactures false confidence. The 28 tests pin the matching, lookup, and comparison logic against fixture workbooks.
Built for a non-author to run, because that was the actual requirement
The inherited script had 21 hardcoded D:\ paths, wrote output to one person's Downloads folder, had a single function, one print statement and no tests. It worked on exactly one machine. What I specified instead discovers its inputs from a folder, fails fast with a diagnostic naming the columns it actually found, writes a timestamped log every run, and ships with a README aimed at a non-technical colleague — because the person who runs it every day is not me. That is a maintainability argument, not a cleverness one.
Three states, not two: pass, fail, and warn
The validator refuses to score what it cannot verify. If the reference resolves, a mismatch is a failure. If the reference is missing or the key is ambiguous, an empty cell becomes a warning rather than a false failure — while a populated cell that cannot be confirmed stays a failure. Same instinct as the margin rule in ReportSense: an unverifiable case becomes visible work, never a silent verdict.

§05Outcome

  • Client escalations on that report stopped after the validator became part of the daily pre-delivery routine.
  • Checking is now minutes of machine time instead of analyst attention.
  • A sibling tool, the MTM–PCSD Validator, applies the same philosophy to reconciling two master datasets — with every comparison rule in a JSON config so field pairs can change without code changes.

§06It outgrew its brief — and that's a problem

The analyst now deliberately submits the report with some fields left partial, and copies the validator's expected values back into it. The tool crossed from checking the report to helping author it. As evidence that the output is trusted, that's the strongest signal I have.

It is also a design flaw, and nobody designed it. The expected-value engine is now load-bearing for data that never gets independently checked — and a validator that supplies the answer can no longer be said to have verified it. The right fix is either an explicit, tested generate mode, or a second check over the copied fields. I'd want that closed before the tool gets any more trust, not after.

§07What I'd change

  • The warnings are noise and people ignore them. About 88% of rows carry at least one warning, concentrated in three fields whose reference sheets are simply incomplete. The warning state exists so that missing reference data can't masquerade as a report defect — but I never tuned the thresholds after the build, so the failure count is the only signal anyone reads. That sheet needs triaging or suppressing.
  • Nothing enforces that it runs. There's no scheduler and no CI. It runs before delivery because the analyst has the habit, which is not a control.
  • Bus factor of one. Whoever delivers the report runs it, there's no second operator, and the developer who owned the original script has left. That's the same failure that created this work in the first place.
